# تست‌بار (Load Test)

این سند نحوهٔ اجرای ابزار تست‌بار پروژه را توضیح می‌دهد:

- `scripts/lib/loadtest-users.ts` — ساخت/پاک‌سازی کاربرهای آزمایشی و مینت کردن
  کوکی نشست (`arena_session`) مستقیماً با jose، بدون لاگین واقعی.
- `scripts/loadtest.ts` — اجرای بار روی سناریوهای `public`، `auth`، `sse` یا `all`
  با autocannon و یک تست‌کنندهٔ SSE دستی، و گزارش PASS/FAIL.

## ⚠️ هرگز روی تولید (Production) تست‌بار واقعی اجرا نکنید

آدرس تولید `http://89.42.199.174` است. **در طول رویداد** (وقتی کاربران واقعی روی
همین سرور تک‌پردازه‌ای/SQLite در حال بازی‌کردن‌اند) تست‌بار اجرا نکنید — حتی یک
تست کوتاه با هم‌روندی بالا می‌تواند SQLite (فایل تک و WAL) و پردازهٔ Node تک‌نخی
Next.js را که کاربران واقعی هم رویش هستند کند یا قفل کند. تنها استثنا: یک
dry-run بسیار محدود و *غیرلاگین* (GET، حداکثر ۵ اتصال، حداکثر ۱۰ ثانیه، فقط
`/` و `/api/phase`) پیش از رویداد برای اطمینان از بالا بودن سرویس — همان چیزی که
در پایین این سند به‌عنوان نمونهٔ dry-run آمده. هیچ‌وقت کاربر آزمایشی روی تولید
نسازید و هیچ‌وقت POST به تولید نفرستید.

تست‌بار واقعی (سناریوهای `auth`/`sse`/`all` و اتصال/مدت بالا) فقط روی **استیجینگ**
مجاز است: `http://89.42.199.174:8080` — یک استک جدا با دیتابیس و `SESSION_SECRET`
مخصوص خودش (تیم دیگری آن را برپا می‌کند)، که رفتار Caddy/Next را عیناً شبیه‌سازی
می‌کند بدون خطر برای بازیکنان واقعی.

## جریان کار روی استیجینگ

۱. **ساخت کاربرهای آزمایشی داخل کانتینر tools استیجینگ** (جایی که `DATABASE_URL`
   و `SESSION_SECRET` استیجینگ در دسترس‌اند — معمولاً با `docker compose exec` یا
   مشابه آن وارد کانتینر شوید):

   ```bash
   DATABASE_URL="file:/path/to/staging.db" \
   SESSION_SECRET="<همان مقدار استیجینگ>" \
   npx tsx scripts/lib/loadtest-users.ts --count 300 --out /tmp/loadtest-cookies.json
   ```

   خروجی: فایل JSON شامل ایمیل/شناسهٔ کاربر/کوکی هر کاربر آزمایشی
   (`lt-0@loadtest.local` .. `lt-299@loadtest.local`).

   > نکته: هر دو متغیر باید *صریحاً* داده شوند؛ اسکریپت عمداً هیچ مقدار
   > پیش‌فرضی برای آن‌ها ندارد تا با اتصال تصادفی به دیتابیس اشتباه (مثلاً `dev.db`
   > محلی) رکورد آزمایشی در آن ساخته نشود.

۲. **کپی فایل کوکی‌ها بیرون از کانتینر** (به لپ‌تاپ یا خود سرور، هرجا قرار است
   `loadtest.ts` اجرا شود):

   ```bash
   docker cp staging-tools:/tmp/loadtest-cookies.json ./loadtest-cookies.json
   ```

   (یا معادل آن بسته به نحوهٔ اجرای کانتینر ابزار استیجینگ.)

۳. **اجرای تست‌بار** از لپ‌تاپ یا از روی خود سرور، رو به `http://89.42.199.174:8080`:

   ```bash
   npx tsx scripts/loadtest.ts \
     --base http://89.42.199.174:8080 \
     --scenario all \
     --connections 100 \
     --duration 30 \
     --sse 100 \
     --cookies ./loadtest-cookies.json
   ```

۴. **پاک‌سازی** کاربرهای آزمایشی از دیتابیس استیجینگ (دوباره داخل کانتینر tools،
   با همان `DATABASE_URL` استیجینگ):

   ```bash
   DATABASE_URL="file:/path/to/staging.db" npx tsx scripts/lib/loadtest-users.ts --cleanup
   ```

   این حذف تمام کاربرهایی با الگوی ایمیل `lt-*@loadtest.local` و رکوردهای وابسته
   (اعلان‌ها، اشتراک‌های push، پیشنهادهای حراج، خریدها، سرمایه‌گذاری‌ها، پیام‌های
   دیوجنس، دفتر کل، دعوت‌نامه‌ها) را به ترتیب ایمن نسبت به کلید خارجی انجام می‌دهد،
   سپس خود کاربرها را حذف می‌کند.

## سناریوها

| سناریو | نیاز به `--cookies` | چه چیزی را می‌سنجد |
|---|---|---|
| `public` | خیر | ترکیب وزن‌دار GET بدون لاگین: `/`، `/api/phase`، `/api/market/ticker`، `/api/auction/live` |
| `auth` | بله | ترکیب وزن‌دار GET لاگین‌شده (کوکی‌ها بین درخواست‌ها چرخانده می‌شوند): `/market`، `/leaderboard`، `/api/notifications`، `/auction` |
| `sse` | بله | N اتصال هم‌زمان SSE به `/api/auction/stream` (با `--sse`)، **هم‌زمان** با بار `public` تا فن‌اوت (fan-out) زیر بار واقعی سنجیده شود |
| `all` | بله | `sse` + `public` + `auth` با هم |

پرچم‌های اصلی: `--base URL`، `--duration ثانیه`، `--connections عدد`،
`--scenario public|auth|sse|all`، `--cookies file.json`، `--sse عدد` (تعداد
اتصال SSE هم‌زمان)، و `--paths /a,/b` برای محدود کردن مسیرهای سناریوی `public`
(مثلاً برای یک dry-run امن روی تولید که فقط اجازهٔ دو مسیر مشخص را دارد).

آستانه‌ها با `--threshold-api-p95`، `--threshold-page-p95`،
`--threshold-error-rate` و `--threshold-sse-established` قابل تنظیم‌اند
(مقادیر پیش‌فرض در جدول زیر).

## آستانه‌های PASS/FAIL

| معیار | آستانه |
|---|---|
| p95 لتنسی API‌ها | کمتر از ۵۰۰ میلی‌ثانیه |
| p95 لتنسی صفحات | کمتر از ۱۵۰۰ میلی‌ثانیه |
| نرخ خطا (non-2xx + خطای اتصال) | کمتر از ۱٪ |
| نرخ برقراری اتصال SSE | حداقل ۹۹٪ |

اگر هر یک از این‌ها رد شود، خروجی برنامه `1` است (برای استفاده در CI/اسکریپت).
گزارش کامل هم در ترمینال (جدول فارسی+انگلیسی) و هم به‌صورت JSON در
`./loadtest-report-<timestamp>.json` نوشته می‌شود.

**این فایل‌های `loadtest-report-*.json` و هر فایل کوکی (`*cookies*.json`) را
کامیت نکنید** — حاوی توکن نشست کاربرهای آزمایشی‌اند و صرفاً خروجی محلی/موقت این
ابزارند؛ اگر پروژه گیت داشته باشد باید به `.gitignore` اضافه شوند.

## چگونگی خواندن نتایج

- هر ردیف جدول یک «گروه» است (مثلاً `public-pages` یا `auth-apis`)؛ چون آستانهٔ
  p95 برای صفحه و API فرق دارد، هر سناریو به دو گروه صفحه/API تقسیم می‌شود و
  اتصال‌های `--connections` متناسب با وزن هر گروه بین آن‌ها تقسیم می‌شود.
- `req/s` = درخواست موفق تکمیل‌شده بر ثانیه، `p50/p95/p99` = صدک‌های لتنسی
  محاسبه‌شده از تک‌تک پاسخ‌ها (نه فقط تخمین داخلی autocannon)، `non-2xx` =
  تعداد پاسخ‌های غیر ۲xx، `err%` = (non-2xx + خطای اتصال) ÷ کل تلاش‌ها.
- برای SSE: `Established` باید نزدیک ۱۰۰٪ باشد (یعنی اتصال SSE واقعاً برقرار
  و جریان باز شده)، `p50/p95` لتنسی اولین رویداد از لحظهٔ ارسال درخواست تا
  اولین قطعهٔ SSE (شامل کامنت `connected` اولیه) است، و میانگین «رویداد در
  دقیقه» نشان می‌دهد سرور زیر بار چقدر مرتب heartbeat/state می‌فرستد (روال عادی
  حدود ۴ در دقیقه از heartbeat ۱۵ثانیه‌ای، به‌علاوهٔ رویدادهای واقعی state).

## اهداف تقریبی ۱۰۰/۲۰۰/۳۰۰ کاربر هم‌زمان

اینها راهنمای شروع‌اند، نه قانون سخت؛ روی سخت‌افزار واقعی سرور کالیبره کنید:

- **۱۰۰ کاربر** (`--connections 100 --sse 100`، سناریوی `all`): باید به‌راحتی
  همهٔ آستانه‌های بالا را PASS کند. اگر اینجا FAIL شد، مشکل زیرساختی است
  (نه فقط ظرفیت) و باید پیش از رویداد حل شود.
- **۲۰۰ کاربر** (`--connections 200 --sse 200`): سطح تقریبی حداکثر هم‌زمانی
  واقعی رویداد؛ هدف PASS کامل. اگر p95 API نزدیک آستانه شد، به `cached()`
  TTL‌ها (`src/lib/ttl-cache.ts`) و اندازهٔ pool اتصال SQLite نگاه کنید.
  توجه: با یک پردازهٔ Node تک‌نخی، throughput واقعی به تعداد هستهٔ CPU سرور
  محدود می‌شود؛ افزایش `--connections` بعد از یک نقطه فقط صف را طولانی
  می‌کند، نه throughput را.
- **۳۰۰ کاربر** (`--connections 300 --sse 300`): تست حاشیهٔ اطمینان. FAIL در
  این سطح لزوماً بحرانی نیست (تعداد واقعی شرکت‌کنندگان را از برگزارکننده
  بپرسید)، اما اگر نرخ خطا/لتنسی به‌شدت بد شد (نه فقط کمی بالای آستانه)،
  نشان‌دهندهٔ نقطهٔ شکست SQLite/event-loop تک‌پردازه است — مفید برای برنامه‌ریزی
  ظرفیت، نه لزوماً چیزی که باید هدف‌گذاری هم‌زمانی رویداد را عوض کند.

## نمونهٔ dry-run امن (اجراشده در همین جلسه، رو به تولید)

```bash
npx tsx scripts/loadtest.ts \
  --base http://89.42.199.174 \
  --scenario public \
  --connections 3 \
  --duration 8 \
  --paths /api/phase,/
```

این دقیقاً در محدودهٔ مجاز است: بدون لاگین، فقط GET، حداکثر ۵ اتصال (اینجا ۳)،
حداکثر ۱۰ ثانیه (اینجا ۸)، و با `--paths` منحصر به `/api/phase` و `/`.

## تست کاربرهای آزمایشی روی دیتابیس موقت (بدون اتصال به استیجینگ/تولید)

برای اطمینان از درستی مینت/رمزگشایی توکن و پاک‌سازی، بدون لمس هیچ دیتابیس
واقعی، `scripts/lib/loadtest-users.ts` را رو به یک فایل SQLite موقت (مایگریت‌شده
با `prisma migrate deploy`) اجرا کنید:

```bash
DATABASE_URL="file:/tmp/lt.db" npx prisma migrate deploy
DATABASE_URL="file:/tmp/lt.db" SESSION_SECRET="test-secret-minimum-32-characters!!" \
  npx tsx scripts/lib/loadtest-users.ts --count 5 --out /tmp/lt-cookies.json
DATABASE_URL="file:/tmp/lt.db" npx tsx scripts/lib/loadtest-users.ts --cleanup
```
